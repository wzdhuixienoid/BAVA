# 未满足赛题功能的后续实现顺序

计划日期：2026-10-07。当前仍为v0.9.2 / Git `667dd9e`。这是后续路线，以下新增能力尚未实现；原有缺口和问题依据[需求与Bug评估](01-requirements-and-bugs.md)。本次只新增计划文档。

建议顺序：**修复安全缺口 → 补齐核心技术要求 → 强化已有三个场景 → 增加第四、第五场景 → 完成生日联动。** 赛题至少要求三个场景方向，卡片、理财和生日全流程属于后续扩大覆盖；权限、安全、任务规划应先完成。真实银行接入单独作为落地阶段，不能与比赛的Mock演示混为一谈。

## 1. 建议按这个顺序迭代

优先级P0为安全与核心技术，P1为现有场景和渠道完善，P2为扩展场景，P3为真实服务落地。每一步先达到验收条件，再进入依赖它的下一步；不预设团队人数、工期或比赛截止日期。

|---|---|---|---|---|

## 2. 前五步的实现边界

### 第1步：先恢复可证明的安全语义

优先R02和R03，再R01；不要只修改提示词或列举几个正则。模型提案是待验证输入：条件、动作金额、币种、时间和收款人都应保留原文来源；含限制但不支持解析时进入澄清或拒绝。

当前复现脚本断言的是错误行为。修复后把它们转成正确行为回归，增加真实Router→Plan/Workflow→UI路径和恶意模型输出用例；继续验证FALSE零写资源、日累计、并发余额、幂等、授权失效和失败计数。固定小额转账回归通过后再扩展写场景。

同时收口幻觉、注入与失败策略：余额、风险、条件、交易成功等关键文字由typed事实生成或校验；无事实依据的业务结论不输出为已确认结果。加入角色冒充、工具返回中的恶意指令、上下文改金额等对抗用例。统一失败分类与审计；安全失败进入SecurityGuard，连续Provider故障进入服务熔断并暂停新提交，已有UNKNOWN仍按安全协议查询收敛。明确各类阈值、恢复条件和用户可见状态，避免把普通无数据查询当可疑行为。

### 第2步：把对话补全变成结构化业务状态

建议保存intent_id、意图类型、已确认槽位、来源消息、待澄清字段、版本、关联Workflow；模型提出补槽建议，后端校验后更新。金额、币种、收款人、日期等变化必须使相关Approval/强验证失效。

明确区分“联系人标签/收款备注匹配”和“本次转账附言”。完整手机号只在用户有权访问的收款目录中匹配，先解析到银行收款身份并展示掩码，不允许凭任意手机号猜账户；新增或变更收款人另走受控流程。

“照上次转”“给他转点钱”在没有唯一收款人或明确金额时必须澄清。长期记忆可以辅助建议，不能替代当前账户事实和本次授权。

### 第3步：实际身份与强验证要形成闭环

现有OIDC-ready与Mock验证码不是完整验收。需要实际登录配置、身份映射，以及真实独立验证因子。优先实现一个可演示的短信验证Provider；若暂时没有供应商账户，先完成可替换接口和测试Provider，但继续标为Mock，不能宣称真实短信已完成。

验证码发送、验证、失败计数、限流、过期与一次消费都由服务器控制；认证证据绑定用户、会话/挑战、Approval和payload，不跨业务复用。渠道接入后也沿用这一边界，不把验证码交给LLM解析或在普通聊天中提交。

### 第4步：沙箱要有真实执行与隔离证据

首版只允许生成辅助展示/探索脚本，给脱敏只读快照；账户余额、交易金额、风险和业务最终状态继续来自既有确定性Domain。沙箱输出标记来源并校验类型，不直接作为银行事实、权限或写入指令。

执行环境与API隔离，限制CPU/内存/进程数/运行时间/输出大小，默认无网络、无宿主目录/凭证、只读输入与临时输出；结束后清理。记录代码hash、输入hash、资源限制、开始结束、结果/拒绝原因，不记录敏感原始数据。容器只是组成部分，需实际测试文件访问、网络、资源耗尽等隔离边界。

题目将代码沙箱列为核心安全要求，因此应尽早给出实现证据。若组织方确认“禁止生成代码执行”也可满足要求，可调整本步范围；在获得明确口径前，不能把当前无代码入口写成已实现沙箱。

### 第5步：取消与回退遵守已发生的事实

当前已有pause、resume和只读rollback，应补充Plan cancel API、版本/fencing、未开始步骤取消与人工处理备注。已提交Provider的操作不能凭一次cancel变成“未发生”，应继续reconcile并展示最终结果；成功金融操作需要新的受控补偿流程。人工接管同样遵守Approval与强验证。

SSE只作为提示，资源API继续做事实源。先提供断线及事件遗漏时的资源刷新保障，再按部署规模决定是否需要共享通知组件；不要求为单进程比赛Demo一次引入全部消息基础设施。审计同时覆盖取消、接管、恢复和失败原因。

## 3. 后续场景的关键依赖

### 年报与续费提醒：第6步拆成两个小交付

6A先做年度统计/报告：复用Decimal、按用户/账户/币种聚合、报告证据校验，增加覆盖月份和缺失数据说明。当前fixture不含完整全年流水，应新增有明确来源的合成全年数据，不能用少量月份推断全年。导出使用已生成的可信报告，不重新让模型计算金额。

6B再做主动提醒：新增Reminder状态、自然日/时区、合同续费规则、用户同意的通知渠道、去重key和取消规则。到时扫描可复用持久调度模式，但Reminder必须是独立业务资源；不要改写只读reference clock去模拟真实到期。无用户通知授权时仅展示应用内通知。

### 定时支付：预约授权不能复用十分钟Approval

调度器只负责到期唤醒；执行时重新检查身份、账户、余额、日累计、Guard、预约版本和有效授权。预约取消/改期与到期claim竞争要有事务与fencing保护。

可以分两版：第一版“预约→到期创建待确认业务”是**预约待办**；第二版引入明确的ScheduledMandate，绑定收款人、账户、金额、币种、执行时刻/有效窗口、次数、撤销状态，才支持约定范围内自动定时执行。Mandate是新领域授权，不能把现有Approval/Reauth TTL延长到几天当作完成。

RED仍需满足执行时有效强验证；到期累计升级RED而无有效认证时进入WAITING_USER/延后或到期失败，不自动扣款。不支持的定时句式在前期就明确拒绝，不能立即转账。二版完成前不要标“自动定时转账COMPLETE”。

### AA：先做精确分账，再做真实收款状态

金额按最小货币单位整数分配，确定尾差归属并展示；每位参与者只授权自己的付款，发起人不能替别人确认。当前Mock只扣付款余额，没有收款入账，因此需增加入账/结算账务和匹配依据。

拆分草稿、收款请求、提醒、支付成功、到账是不同事实。首版可先完成请求管理，再补独立付款与最终收款；在Provider确认前保持待支付/待到账。向其他人发送邀请或催款须有用户明确授权。

### 卡片、理财：先查询，再新增确定性写Workflow

第10步按“卡查询→虚拟卡申请→交易限制→挂失/解挂→额度调整/其他申请”推进。新增工具采用显式注册和默认拒绝；挂失/解挂按题意RED，其他新动作先定义风险策略再开放。每种动作需要自己的typed状态和Provider最终事实。

第11步按“产品目录与对比→风险问卷及适配规则→申购→赎回”推进。产品风险、期限、费用和收益口径都应有可追溯来源；如未来接入非结构化说明，可增加检索，但实时价格、份额和收益仍走Domain/Provider。申购RED；赎回明确独立策略。购买受理不等于成交，赎回受理不等于到账。

### 生日：必须最后组合已有、已验收的能力

第12步先定义可用余额与Hold/Release/Capture：预留1000应减少可支用资金，重复预留不能多扣，失效/取消能够释放。再开放多写DAG；不能只把max_write_steps从1改大。每一步拥有自己的Workflow、授权、幂等key、恢复与补偿规则。

第13步再接生日：用户明确保存生日、时区、预算、日期、收货人与地址；计划包含预留、到期触发、询价/库存、订单确认、付款与订单结果。价格超预算/缺货/生日日期歧义需等待用户；已发货、已扣款等状态决定可用补偿，不能把整图“回退”包装成银行转账撤销。

## 4. 推荐的交付里程碑

| 里程碑 | 包含步骤 | 能对外说明什么 |
|---|---|---|
| A：核心技术补齐 | 1–5 | 既有安全问题修复，多轮澄清、实际强验证、代码沙箱、取消/接管具备验收证据 |
| B：现有场景强化 | 6–8 | 年报、主动提醒、定时业务和一个外部渠道形成链路；定时自动执行须按二版实际状态表述 |
| C：扩大场景覆盖 | 9–11 | 补AA，新增卡片与理财方向；每条新增写路径独立验收 |
| D：完整跨场景联动 | 12–13 | 多写、安全预留、补偿与生日计划可完整演示 |
| E：真实服务落地 | 14 | 在已授权的银行/商户测试环境验证Provider和对账；生产上线另按实际接入要求验收 |

若比赛时间有限，先完成A，再完成B中能稳定验收的功能；随后优先卡片管理作为第四场景，再考虑理财与生日。AA、卡片、理财之间没有强制依赖，排期紧张时可以调换9–11；生日依赖预约、资金预留和多写恢复，必须保留后置顺序。

通用验收要求：每次迭代更新README、需求覆盖表、架构图、网页用例与证据；新增写Workflow必须验证未授权零写入、强验证/TTL、改草稿失效、owner隔离、重复提交、并发、UNKNOWN恢复与审计。现有原型能力、计划能力与真实外部接入状态分别注明，不提前标COMPLETE。

沿用[Architecture Baseline](../docs/architecture-baseline-v0.1.md)：模块化单体、结构化状态、Workflow First、Default Deny。不需要为了这些需求先上自由Multi-Agent、微服务或向量库；按实际问题引入必要组件。
